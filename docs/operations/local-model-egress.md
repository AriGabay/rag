# חיבור הסביבה המקומית לספק המודל

הצ׳אט פועל בסביבת Docker Compose של הפרויקט: `db`, `backend`, `worker` ו־`frontend`, מופע אחד מכל אחד. המפתח
(`OPENAI_KEY` ב־`.env`) נקרא רק בצד השרת, ואינו מודפס בשום בדיקה.

## הפעלה ועצירה

```bash
docker compose up -d --build
```

```bash
docker compose stop
```

- הצ׳אט: `http://localhost:3000/chat`.
- לאחר שינוי קוד בצד השרת, בונים מחדש ומפעילים מחדש רק את שירותי השרת:

  ```bash
  docker compose build migrate && docker compose up -d --force-recreate backend worker
  ```

## בדיקת החיבור

```bash
scripts/check-model-egress.sh
```

הסקריפט רץ בתוך `backend` ובתוך `worker`, בודק שכבה אחר שכבה ומדפיס סטטוסים בלבד:

1. **DNS:** הכתובות של `api.openai.com`, ושל מארח ביקורת (`cloudflare.com`) מאחורי אותו CDN.
2. **TCP:** חיבור ל־443 בכל כתובת.
3. **TLS:** לחיצת יד עם אימות תעודה (SNI), הגרסה והגורם המנפיק.
4. **Proxy:** שמות משתני ה־proxy המוגדרים, אם יש.
5. **HTTPS:** קריאה ל־`/v1/models` בלי מפתח (צפוי 401) ועם המפתח המוגדר (צפוי 200). קוד הסטטוס בלבד.
6. **בדיקת החיבור של האפליקציה:** הנחיה סינתטית דרך הספק המוגדר.

## האבחון (7 באוקטובר 2026)

**בסבב הקודם:**
- מתוך המיכלים, חיבור TCP לכתובות של `api.openai.com` נכשל בפסק זמן, בעוד שמארחים אחרים מאחורי אותו CDN התחברו.
- הרצות המודל האמיתי בוצעו אז עם `backend` ו־`worker` שרצו על המארח.

**באבחון הנוכחי, לאחר שהמיכלים נוצרו מחדש, כל השכבות תקינות בשני המיכלים:**
- DNS מחזיר את כתובות ה־IPv4 וה־IPv6.
- TCP מתחבר לכתובות ה־IPv4.
- TLS 1.3 עם תעודה מאומתת (Google Trust Services).
- אין משתני proxy.
- הקריאה ל־`/v1/models` מחזירה 401 בלי מפתח ו־200 עם המפתח.
- בדיקת החיבור של האפליקציה עוברת.

ממצאים נוספים:
- **IPv6 אינו זמין במיכלים.** החיבור נכשל מיד (`OSError`), כך שהלקוח עובר ל־IPv4 בלי עיכוב.
- **אין רכיב מקומי שמיירט בצד המארח.** `curl` במארח מתחבר דרך `127.0.0.1`, אבל זה ה־proxy של סביבת הפקודות של
  סוכן הקוד, לא רכיב של המשתמש: אין משתני proxy, אין `~/.curlrc`, ואין מאזין מקומי על 443.
- **מותקן במחשב VPN מבוסס packet tunnel (Surfshark WireGuard), שהיה מנותק בזמן האבחון.** VPN כזה מנתב גם את
  התעבורה של Docker Desktop. זה החשוד הסביר לחסימה הסלקטיבית של כתובות הספק בסבב הקודם, אבל זה לא הוכח.

**לכן לא נדרש שינוי בקובץ ה־compose. לא שונו הגדרות Docker גלובליות, ולא הוסף CA למיכלים.**

## אם החיבור נכשל שוב

1. הריצו `scripts/check-model-egress.sh` ומצאו את השכבה הראשונה שנכשלת.
2. **TCP נכשל לכתובות הספק בלבד** (מארח הביקורת מצליח):
   - בדקו אם VPN או מסנן רשת פעיל במארח (`scutil --nc list`), ונסו לנתק אותו או להחריג ממנו את Docker Desktop.
   - לאחר שינוי, צרו מחדש את שירותי השרת בלבד:

     ```bash
     docker compose up -d --force-recreate backend worker
     ```
3. **TLS נכשל באימות תעודה:** רכיב ביניים מפענח את התעבורה. אל תכבו אימות TLS. הוספת CA למיכלים היא החלטה של
   המשתמש, ואינה מבוצעת אוטומטית.
4. **רק כשאין דרך אחרת,** הריצו את השרת על המארח לפי
   `docs/solutions/workflow-issues/real-model-before-after-eval-on-the-local-stack.md`.
   - עצרו קודם את `backend` ו־`worker` של compose, כדי שלא ירוצו שני מופעים:

     ```bash
     docker compose stop backend worker
     ```

## שרת על המארח לצד Docker: אחסון משותף ועובד אחד

שרת שרץ על המארח משתמש בתיקיית קבצים משלו (`FILE_STORAGE_ROOT`), ולא ב־volume של compose:
- **העלאה דרך שרת המארח:** הקובץ נשמר בתיקייה של המארח, ועובד ה־compose נכשל עליו ב־`FileNotFoundError`.
- **שני עובדים על אותו מסד:** הם מושכים עבודות מאותו תור.

לכן, כשמריצים את השרת על המארח:
- עוצרים את `backend` ו־`worker` של compose (`docker compose stop backend worker`);
- מריצים על המארח שרת אחד ועובד אחד, שמצביעים על אותה תיקיית קבצים;
- בסיום מחזירים את שירותי compose ועוצרים את תהליכי המארח, כדי שלא ירוצו שני שרתים או שני עובדים על אותו מסד.

אף פעם לא מוחקים מסד, מסמכים או גיבויים כדי לסדר את הסביבה.
